OptiTrack VR Multiplayer Plugin

A co-located multiplayer PCVR framework for Unreal Engine 5.8 that anchors each headset to OptiTrack while keeping the headset's own orientation and prediction, cutting fast-motion tracking error from centimeters to millimeters.

  • Unreal Engine 5.8
  • C++
  • OpenXR
  • Multiplayer VR
  • OptiTrack
Read the technical manual ↗

Project overview

Purpose
Let several people share one physical room in VR (six stations by default), with every headset anchored to OptiTrack so players, avatars and the real space stay registered, without giving up the headset runtime's low-latency orientation and motion prediction.
Audience
Unreal Engine developers and venue operators building co-located, location-based VR and mixed reality experiences.
My role
Developer (tracking fusion, OpenXR integration, multiplayer framework and tools)
Timeframe
2026
Platform
Unreal Engine 5.8 C++ plugin, version 0.3.0 beta (Win64 PCVR), OpenXR, OptiTrack Motive via Live Link. Tested on Meta Quest 3 over Link and Air Link.

The problem

When several people share one physical room in VR, each headset’s own inside-out tracking lives in its own coordinate space and drifts over time. Players stop lining up with each other, avatars float, and virtual objects slip away from the real room.

OptiTrack gives precise, room-wide positions, but simply replacing the headset’s pose with optical data throws away the runtime’s orientation and short-horizon prediction. The result lags and judders, especially during fast head turns. This plugin fuses the two instead: Motive anchors absolute position, and the OpenXR runtime keeps orientation and predicted motion.

Your contribution

  • Tracking fusion: combines OptiTrack position with the headset’s OpenXR pose at matched capture times, with a filtered correction and graceful fallback states
  • OpenXR integration: a modified UE 5.8 OpenXR plugin that injects the fused position on both the game and render threads, while runtime orientation stays intact
  • Calibration and alignment: a guided eye-pivot and walking-yaw workflow, plus automatic alignment during normal use
  • Multiplayer session framework: a LAN dedicated server with physical host stations, readiness checks, replicated head and hand poses, and late-join handling
  • Shared mixed reality: host-controlled passthrough modes with per-actor content rules
  • Stereo HUD: UMG menus rendered into an OpenXR compositor layer for readable text, with hand-ray interaction
  • Documentation: a 12-page technical manual for developers and venue operators

System architecture

Tracking is solved on each VR client. The dedicated server never receives Motive data; it owns the shared session state and relays participant data.

Key decisions

1. Fuse instead of replace

The plugin compares the two trackers at the same capture time, then adds a filtered correction to the runtime’s predicted display-time position. The filter runs on the correction, not on the head motion, so the headset keeps its own low-latency prediction.

C = inverse(T) * MotiveEye(t_capture) - Runtime(t_capture)
Output(t_display) = RuntimePredicted(t_display) + Filtered(C)

T = the VROrigin tracking-to-world transform

The tested Meta runtime doesn’t return reliable poses for past times, so the plugin keeps its own history of runtime poses and interpolates it at each optical capture time.

2. Degrade gracefully when a tracker drops out

Markers get occluded and headsets get taken off. Instead of snapping, the plugin moves through explicit states:

State Behavior
Fusion Normal operation: runtime prediction plus the filtered optical correction
Hold Optical gap over 0.15 s: keep the last correction while runtime tracking carries motion
OpticalOnly Runtime position untracked: predict from fresh optical data, up to 0.15 s ahead
Coast Both sources unavailable: hold the last output for up to 0.5 s, then hand back to the runtime
Init After put-on or reacquisition: prefer fresh optical data, then the last correction
NoOptical / Doffed No usable optical data, or headset removed: use runtime tracking

Small corrections are absorbed smoothly: the play space re-anchors in XY at up to 6 cm/s, and yaw is servoed at up to 0.2°/s while the player stands still.

3. Calibration an operator can run on site

Accurate co-location depends on knowing where the eyes are relative to the markers. A guided two-stage workflow solves it:

  1. Eye pivot: the player nods and turns their head through a guided sequence; the solve estimates the pivot-to-eye offset and rejects results with residuals above 2 cm.
  2. Walking yaw: the player walks about 4 m with a level head; the solve separates world yaw from the marker mount’s fixed yaw offset, which a stationary comparison can’t do.

Results are saved per headset on each PC. A clear green “aligned” status uses hysteresis: it turns on at 1° of yaw error or less, and turns off only if the error stays above 2° for 2 seconds.

4. A session model built for a physical venue

  • The host is a physical station, not whoever connects first, and host status follows that station across reconnects.
  • A player is ready only when four checks pass: valid OpenXR pose, headset on head, fresh OptiTrack tracking and an aligned verdict. Status is sampled at 4 Hz and sent reliably only when something changes.
  • Head and hand poses go to the server through unreliable RPCs at a set rate, and remote copies interpolate toward them.
  • Shared scene changes are requested by the host, re-validated on the server, and replicated as a single state with a change serial, so late joiners apply the current mode immediately.

Results and learning

Condition Legacy RMS Fusion RMS
Fast yaw, 150–239°/s mean, peaks to 479°/s 3–8 cm 0.15–0.62 cm
Walking, about 1 m/s 5–7 cm 0.10–0.35 cm, 0 snaps
Rest 0.10–0.18 cm 0.03–0.12 cm

RMS compares logged display-time poses with the optical eye position at the matching capture time. These are development results, not a guaranteed accuracy or motion-to-photon latency.

What I learned

  • Calibration matters as much as the algorithm: a later fast-yaw run with a zero pivot-to-eye offset showed about 1.3 cm RMS and around −40 ms apparent lag.
  • Wireless transport is its own problem. Fusion can’t fix Link packet loss, and venue logs showed much lower loss over USB.
  • Air Link’s HEVC codec produced offset passthrough edges in testing, so the documented path uses H.264.
  • Environment-depth occlusion was removed after severe Air Link degradation. Knowing what to cut was part of shipping.

Next steps: a controlled physical registration test to confirm millimeter-level accuracy, wider recenter and re-localization coverage, and validation at the full participant count.
